These should be explicit parts of the ECAS UI roadmap, not treated as optional graphing enhancements. They represent two distinct scientific visualization needs:

1. Transit analysis: a light curve synchronized with a 3D orbital/transit animation, including a time or observation-position tracker, playback controls, adjustable speed, and wavelength information.
2. Molecular spectroscopy: dedicated visualization of molecular reference spectra, with enough space and controls to inspect spectral features and their metadata.

Both belong in the proposed Analysis workspace, but they need different visualization designs and scientific requirements.

## 1. Transit analysis: proposed visualization design

The earlier ECAS implementation is a useful reference point. Before recreating it, we should inspect the original `ECAS` repository to identify what can be recovered, what needs adaptation, and what was lost or changed in `ECAS_BETA`.

PRIMARY VISUALIZATION

## Transit light curve + orbital model

The light curve and 3D model should occupy the same analysis view and remain synchronized to a shared observation position.

[svs.gsfc.nasa.gov](https://svs.gsfc.nasa.gov/11413?utm_source=chatgpt.com)

Light curve panel

- Display measured flux or normalized brightness against time or orbital phase, according to the dataset.
- Show the current observation position with a movable tracker.
- Update the tracker as the animation plays.
- Display relevant observation metadata and wavelength information, when the dataset actually provides it.

3D orbital model

- Show the planet moving across the star from a clearly defined viewing perspective.
- Synchronize its position with the selected point on the light curve.
- Support play, pause, stepping, scrubbing, and adjustable playback speed.
- Allow camera rotation and reset without altering the underlying observation position.

Shared controls and readout

- Current timestamp or orbital phase.
- Current wavelength or spectral channel, if available.
- Playback speed and animation state.
- Clear indication of whether the position is measured, interpolated, or generated by a model.

### Important scientific design requirement

The tracker should not merely animate a planet at an arbitrary speed. Its relationship to the data must be defined.

For a time-series observation, the selected observation timestamp should drive the corresponding model position. For wavelength-resolved transit data, wavelength may be a separate dimension rather than a value that changes with time. If the data contains multiple wavelength channels, the interface may need a channel selector alongside the time tracker.

The exact synchronization model should be recovered from the original implementation if possible. We should not assume that every dataset contains both time and wavelength information.

### Where it belongs

The transit visualization should be a dedicated analysis mode, available both from the general Analysis workspace and from within a project.

- Scratch session: explore a transit dataset without creating a project.
- Project context: work with the project's selected transit data and retain supported analysis settings and results.
- Layout: allow the light curve and 3D model to be resized, with a way to emphasize either one.
- Fallback: datasets lacking the required fields should still be inspectable, with unsupported animation controls disabled and the reason explained.

I would treat the synchronized light curve and orbital model as a major future feature, not something to squeeze into a small graph panel.

Main plot

- Wavelength or wavenumber on the horizontal axis, with the axis type and units clearly identified.
- The correct spectral quantity on the vertical axis, including its units.
- Zoom, pan, range selection, and reset controls.
- A readable trace legend and the ability to inspect selected points.
- Support for multiple traces when the data are compatible and the user explicitly selects them.

Metadata panel

- Molecule and isotopologue.
- Provider, dataset identifier, and source link.
- Temperature, spectral coverage, resolution or spacing, and other available conditions.
- Product type and units.
- Cache status and retrieval provenance.

Contextual actions

- Open or retrieve a supported reference.
- Reopen a cached reference.
- Add the reference to a scratch session or project.
- Send it to a supported analysis workflow when its requirements are met.

The plot should use most of the available workspace. Metadata can live in a collapsible inspector, and long technical descriptions should not crowd out the spectrum.

The current ExoMol integration's narrow CO₂ retrieval support must remain clearly distinguished from the broader searchable catalogue. A catalogue record is not necessarily a retrievable spectrum, and a retrieved spectrum is not automatically eligible for scientific comparison.

## 3. How these fit into the larger roadmap

I would now separate Analysis into several explicit modes, while keeping the underlying workspace shared.

| Analysis mode       | Main visual emphasis                      | Purpose                                                        |
| ------------------- | ----------------------------------------- | -------------------------------------------------------------- |
| Transit analysis    | Large light curve + synchronized 3D model | Inspect transit observations and orbital geometry              |
| Spectrum inspection | Large spectral plot                       | Inspect observational or molecular spectra                     |
| Spectrum comparison | Multiple coordinated traces               | Compare compatible datasets under explicit rules               |
| Diagnostics         | Method-specific plots and tables          | Examine supported fitting, uncertainty, and validation results |

These are planned capabilities, not claims that all four currently exist.

A sensible implementation sequence is:

1. Inspect the original ECAS repository. Locate the prior light curve, 3D orbital model, tracker, playback controls, and wavelength readout. Record their dependencies and data assumptions.
2. Inventory current ECAS_BETA capabilities. Determine what existing plotting, data models, persistence, and project services can support these designs.
3. Design the shared visualization framework. Define reusable plot controls, selection state, legends, metadata inspectors, resizing, and recovery behavior.
4. Design the molecular spectrum inspector. This builds on the existing reference-retrieval work and provides a concrete path to better visualization.
5. Plan transit synchronization separately. Specify the relationship among timestamps, light-curve points, wavelength channels, and 3D position before implementing animation.
6. Integrate and verify incrementally. Test scratch and project contexts, saved state, missing fields, large datasets, playback behavior, and scientific axis/units handling.

The first task should be recovering the old transit implementation and comparing it with the current beta architecture. That will tell us whether the best path is to reuse existing code, adapt parts of it, or rebuild the visualization while preserving its original behavior.

## 2. The wavelength behavior is tied to a second data dimension

The most important additional finding is in [`app/core/timeseries.py`](https://github.com/brettadin/ecas/blob/main/app/core/timeseries.py?utm_source=chatgpt.com).

The original implementation distinguishes ordinary photometry from a wavelength-resolved spectral time series:

- `LightCurve` holds time and flux, with optional flux uncertainties.
- `SpectralTimeSeries` holds a time array, a wavelength array, and a two-dimensional flux matrix indexed by time and wavelength.
- `relative_spectrum_at()` extracts the spectrum corresponding to the current observation time, relative to an out-of-transit reference spectrum.
- `transmission_spectrum()` derives a transit-depth spectrum from the wavelength-resolved time series.

This means the original design already had the foundation for displaying the spectrum at the currently selected transit time.

The UI includes a `Spectrum at t` chart tab. As the shared clock moves, the displayed spectrum can be updated for that time. This is distinct from the light curve: one shows how brightness changes over time, while the other shows how measured flux varies with wavelength at a selected time.

One scientific distinction matters here: the spectrum-at-time view and the extracted transmission spectrum are not interchangeable. The first represents a time-selected spectrum normalized against an out-of-transit reference; the second represents derived wavelength-dependent transit depths.

The implementation also contains a separate transmission-depth plot with uncertainty bars, a model-residual plot, noise diagnostics, and an abundance-profile plot. These provide useful precedent for the larger Analysis workspace.

## 4. How I would carry this into the new UI plan

I would now make the following requirements explicit.

## Transit Analysis workspace

Design requirement

Primary view: a resizable arrangement of the light curve, orbital visualization, and observer view.

Persistent playback controls: play/pause, scrubber, speed, time, phase, and relevant data readouts.

Synchronized spectral view: when wavelength-resolved data are available, display the spectrum at the selected time and identify the selected wavelength or channel when applicable.

Additional analysis views: phase-folded curve, extracted transmission spectrum, model residuals, noise diagnostics, and atmospheric-model diagnostics, each available in an appropriate tab or panel.

Context: the same tools must work in scratch sessions and project analysis.

Scientific safeguards: clearly distinguish observed data, fitted transit curves, simulated orbital positions, extracted spectra, and forward-model results.

## Molecular Spectrum Inspector

Design requirement

Primary view: a large, interactive spectral plot.

Context: molecule, isotopologue, source, dataset, units, temperature, spectral range, and other available conditions.

Actions: inspect, zoom, retrieve when supported, reopen cached references, and send compatible data to analysis.

Scientific safeguards: do not imply that a reference spectrum is a measured planetary spectrum or that two spectra are directly comparable just because both can be plotted.

## 5. One important UI improvement over the original

The original `TransitPanel` places a wide control sidebar beside a vertical stack of charts and the two orbital views. It also puts playback controls below those views. This is functional, but it gives the control panel considerable space and can leave the main visualizations competing for height.

For the redesign, I recommend:

- Put the light curve and orbital visualization at the center of the workspace.
- Keep playback controls in a compact, persistent strip immediately below the primary visualizations.
- Move advanced scientific parameters into a collapsible settings panel.
- Make secondary plots accessible through tabs or selectable panels, with user-controlled sizing.
- Let users enlarge the light curve or orbital view when either needs closer inspection.
- Keep the selected dataset and its provenance visible without forcing the user to keep a large metadata panel open.

That preserves the original behavior while giving the visualizations more room and making the interface more adaptable.

## 6. What remains to be verified before implementation

This review establishes the original implementation's structure and behavior. It does not establish which parts can be transplanted directly into `ECAS_BETA`.

The next planning step should compare the original modules against the current beta repository, especially:

1. Whether the beta data models can represent the original `LightCurve` and `SpectralTimeSeries` structures without duplicating existing functionality.
2. Whether the transit calculations and wavelength-resolved extraction logic can be reused independently of the old panel.
3. Which dependencies are required for the 3D viewport and which fallback behavior should be retained.
4. How the original panel's capture/restore methods and project persistence interact with beta's newer project and dataset architecture.
5. Which plots and diagnostic functions already exist in beta, so the redesigned UI does not accidentally reimplement them.

Planning conclusion: the original ECAS repository provides a concrete behavioral specification for transit visualization, including synchronized orbital motion, playback, and a spectrum that changes with observation time. The future UI should preserve those capabilities, integrate them into the shared Analysis workspace, and give molecular reference spectra their own equally deliberate inspection experience.
